## Decisions

- **Lockout scope (Ibrahim, 2026-10-07):** the account lockout refuses password, recovery-code
  and TOTP-confirm attempts; passkey sign-in stays open for a locked account (a passkey cannot be
  guessed, and otherwise anyone knowing her email could lock her out). Passkey failures still count
  toward the account and the IP. The IP lockout refuses every sign-in method from that IP.
- **What counts:** failed `signin_passkey`, `signin_password`, `recovery` and `totp` events.
  Registrations (`register`) and sign-outs (`revoke`) are logged, never counted; confirming an
  already confirmed TOTP answers 409 before any attempt (nothing is guessed). A failure counts
  against the account when the attempt identified one (an existing account's email, or the
  passkey's owner), and always against the IP.
- **Lockout length (AUTH-7 "then 15-min lockout"):** a failure that makes 5 inside 15 minutes
  locks for 15 minutes from itself (failures at 0, 1, 2, 3 and 14 minutes lock until minute 29).
  Attempts refused while locked are failures too ("all attempts logged") and count, so steady
  guessing keeps the lock on; `Retry-After` counts the refused attempt itself and is the longer of
  the IP and account waits.
- **Concurrency:** each attempt runs inside a "gate" transaction that takes Postgres advisory
  locks (`auth:ip:<hash>`, `auth:user:<id>`; shared by both API workers) before the lockout check
  and writes its auth event there, so the locks are held until the outcome is recorded. A second
  attempt for the same IP or account while one is in flight is refused (429, `Retry-After: 1`) and
  logged. This closes the burst bypass and makes the TOTP replay check atomic (the success event
  is committed before another attempt can read). At most 4 attempts verify at once per process
  (`asyncio.Semaphore`), bounding Argon2id CPU and the connections held (two per attempt).
  Residual: a crash between the session commit and the gate commit loses that attempt's event.
  Otherwise no attempt goes unlogged: the lockout reads run in a savepoint (a database error cannot
  abort the gate), cancellation is caught too, and if the gate cannot take the event it is written
  in a fresh, shielded transaction.
- **Any error is a failure:** an unexpected exception during an attempt is logged (and counted)
  as a failure before it propagates (500).
- **State:** counted from `auth_events` (durable, append-only per CR-010); no new table for
  lockouts. Migration 0005 adds partial indexes for the three reads (failures by IP and by
  account, TOTP successes by account); indexes only, no table or column change. Residual: refused
  attempts are logged too, so a sustained flood grows `auth_events` (kept a year, T43); T15 should
  add a Cloudflare rate-limiting rule on `/api/v1/auth/*` at the edge.
- **Enumeration and timing:** unknown emails do the same work as wrong passwords (exactly one
  Argon2id verification against a dummy hash, tested; recovery as in T06). After a correct
  password, the TOTP check adds a few milliseconds of decryption; with attempts serialised and
  locked out per account and IP, that difference cannot be sampled usefully. The account lockout
  can still reveal that an email has an account to someone who spreads attempts over many IPs.
- **TOTP replay (12.3):** the step a code matched is not stored (no column), so after a success
  every step up to one past that success's step counts as used; the next code is accepted 30–60 s
  later. Successes are read from `auth_events` (`totp`, `signin_password`), including the confirm.
- **TOTP secret:** 160 bits (`pyotp.random_base32()`), encrypted with her DEK, AAD
  `password_credentials:totp_secret_enc:<user_id>:<user_id>` (the row is keyed by user id).
  Provisioning URI issuer "Life OS", account name her email; returned once, `no-store`.
- **Codes:** spaces are ignored; anything but 6 digits fails as a wrong code; more than 16
  characters is a 422.
- **Passwords:** 12–256 characters (the upper bound limits the Argon2id input; an overlong sign-in
  password is a 422 before any attempt, so it is neither logged nor counted). They are
  NFC-normalised (9.4) at registration and sign-in but not trimmed or otherwise changed (every
  character counts). Refused when `strip().lower()` is on `app/auth/data/common_passwords.txt`
  (30,394 entries: SecLists Pwdb top 1M + NCSC 100k, MIT; stripped, lower-cased, printable, 12–64
  characters). Errors use fixed messages (`password_too_short`, `password_too_common`).
- **Inactive accounts (CR-014):** `require_session` answers 403 problem+json for them;
  `require_any_session` (only `/auth/totp/confirm`) accepts them. If she never confirms, the
  account stays inactive (the admin can delete it, T44).
- **Per-session limit (9.1; CR-016, Ibrahim):** counted in the unlogged `session_request_counts`
  table (fixed 60-second window per session, upserted in the session check's transaction), so it
  is exact across both API workers. It applies through `require_session`, i.e. every signed-in
  endpoint and no auth endpoint.
- **No extra volume limits on the unauthenticated auth endpoints (Ibrahim, 2026-10-07):** spec
  9.1 limits auth endpoints "per section 4.1" only. Locked IPs are refused at sign-in, and expired
  challenges are purged, so the table stays bounded; the residual is challenge-request floods.
  (This answers the T06 note that T07 would add them.)
- **Client-error limit (T10 follow-up):** keyed on the client IP hash, still 20/min, under a
  ceiling of 200/min per process across all IPs; new IPs are refused while 10,000 live keys are
  held. In memory per process (a cost guard against log flooding, not a spec quota).
- **Client IP (CR-015):** `CF-Connecting-IP`, parsed as an IP (a list or junk is refused);
  `X-Forwarded-For` never read. Outside local, `ClientIpRequiredMiddleware` refuses every `/api/`
  request without a valid header (500 problem+json; the probes are exempt for the container
  healthcheck), logging `client_ip.missing` without the value. Addresses in Cloudflare's Workers
  egress range (`2a06:98c0:3600::/48`) count as missing: a cross-zone Pages Function subrequest
  reports that address for every client, which would put everyone in one lockout bucket. **For
  T15:** keep the Pages custom domain and the tunnel hostname in the same Cloudflare zone, and check
  after deploy that real client IPs arrive. Locally the header is honoured when present (tests
  simulate clients), else the socket address.
- **`IP_HMAC_KEY`:** secret file `ip_hmac_key`; outside local required and at least 32 bytes
  (start-up fails otherwise); a fixed development key locally. HMAC-SHA256 of the address, IPv6 by
  its /64 network (one home or server network), IPv4-mapped IPv6 as IPv4. Only the hash is stored
  (`auth_events`, `sessions.ip_hash`); nothing logs the IP.
- **CR-010 grant detail:** `lifeos_jobs` also gets `SELECT (at)` on `auth_events`, which its
  retention `DELETE … WHERE at < …` needs; to be added in the CR-010 spec re-sync. Suggested for
  T43: a SECURITY DEFINER `purge_auth_events()` limited to rows older than a year instead of plain
  DELETE (would amend CR-010; the security reviewer's optional hardening).
- **Sessions** now store `ip_hash` (T06 deferred it here).
