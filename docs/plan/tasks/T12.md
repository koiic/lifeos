- Acceptance criteria, quoted from spec 4.1:
  - AUTH-1: "Invite tokens are single-use, expire after 7 days, stored hashed; `/register` without
    a valid token returns 403"
  - AUTH-2: "Works in iOS Safari 16.4+ and Chrome Android; user verification required"
  - AUTH-3: "Argon2id password hash; TOTP RFC 6238, 30 s, ±1 step"
  - AUTH-4: "Stored hashed; each works once; regenerating invalidates old codes"
  - AUTH-5: "HttpOnly, Secure, SameSite=Lax cookie; 30-day sliding expiry for installed PWA; list
    and revoke sessions in Settings"
  - AUTH-6: "After 5 min in background the app shows a lock screen; unlock with passkey (user
    verification) or a 6-digit PIN"
  - 11.6: "On `visibilitychange` to hidden, store the time. On visible, if more than
    `app_lock_timeout_s` passed (default 300), show the LockScreen overlay over a blurred app.
    Unlock with a passkey (`/auth/reauth`, purpose `unlock`) or her PIN
    (`/auth/app-lock/unlock`). The overlay is rendered before any data, and screens hide content
    when the app is backgrounded so the iOS app switcher snapshot shows the lock state."

## Decisions

Internal choices the spec leaves open (not change requests):

- **Passkey management in Settings (Ibrahim, 2026-10-08):** T12's Security screen includes the
  passkey list, add and remove (T08 built the endpoints; no other task owns their UI).
- **Signed-in check without `/me`:** `GET /auth/sessions` is the probe (`['session']` query) until
  T09's `/me`: 200 signed in, 401 signed out, 403 "not activated" pending (CR-014). Any 401 from
  any query or mutation re-checks it; signed out (also when revoked elsewhere) clears every
  cached query and the lock (11.4). The encrypted persisted cache and outbox (T23) will hook in
  at the same place (`clearLocal`).
- **Refusals told apart by `detail`:** several share a status (403 not activated / recent auth
  required / invalid invite; 401 wrong PIN / PIN lockout). `lib/auth/session.ts` keeps the
  server's messages in one place (`REASON`); the journeys run against the real server.
- **Lock timeout (CR-025):** the spec default (300 s) until `/me` (T09); the Settings control
  belongs to T17 (CR-025), which will also make the "5 minutes" copy follow the setting.
- **Lock state:** time away is checked on both clocks — the monotonic one (cannot be set back,
  but may stop while the phone sleeps) and the wall clock (keeps going in sleep): either past
  the timeout locks; a wall clock earlier than the stored time (set back) locks too. The locked
  state itself is stored, and the store decides it when the page loads, before anything renders,
  so a reload, a cold start or a changed clock never shows her data (security review). Stored
  keys hold only a time and a flag; blocked storage falls back to memory. Signing in starts
  unlocked (an old lock does not carry over).
- **Lock screen (CR-025, Ibrahim 2026-10-08):** opaque `--bg` screen; the app is not rendered
  while locked; the background cover is the same screen with the title only (app kept, inert).
  Above every layer (`z-index: 30`, accepted in CR-025). The passkey button shows only if she has
  a passkey; the PIN field always (409 "no PIN" tells her to use the passkey); a PIN that is not
  6 digits is not sent (each wrong one uses up one of her 5 tries, CR-021).
- **Authenticator setup:** an `otpauth://` link ("Open my authenticator app", the phone she
  registers on is the one with the app) and the key in groups of four; no QR code (she cannot
  scan her own screen, and a QR library is not on the dependency list).
- **Recovery code sign-in:** once the code is accepted it is spent; if the new passkey then
  fails, the message says so and asks for another code (CR-013: no session without a passkey).
- **Recent auth ("Confirm it's you"):** `lib/auth/recentAuth` holds the flow and its dialog
  (built only from `src/ui` components), because three features will need it (settings now; data
  export and account deletion later) and features may not import each other; no new `src/ui`
  component is needed. With a passkey she confirms with it, a password-only account with
  password and code, and while it is unknown (the list failed) both are offered. The action is
  retried once after confirming; cancelling leaves it undone; every opening is a fresh dialog,
  so an abandoned password is not kept.
- **Feedback and focus:** results show inside the section where they happened; only the button
  that started an action shows busy; removing a passkey or the PIN asks first (an alert dialog);
  sign out is a secondary button (not destructive). Offline, every action says it is the
  connection. When a step, mode or message changes, focus moves to the heading (WCAG 2.4.3).
- **Stories:** LockScreen (Locked, WrongPin, Busy, Cover), CodeList (RecoveryCodes), Button
  (Links: primary, secondary, ghost), Stack (Page). CodeList's "copied" and "no clipboard"
  states need a browser action or a missing API, so they are covered by unit tests, not stories.
- **Forms:** React Hook Form with a small Zod resolver (`lib/forms/zodResolver`, no
  `@hookform/resolvers`) and `bindField` for the controlled `src/ui` fields.
- **UI additions:** `LockScreen` (spec 5.5) and `CodeList` (added to 5.5 by CR-025) in `src/ui` (plan 5.3 files, stories, snapshots);
  icons `lock`, `key`, `copy`; `Button` can be a link (`href`); `TextField` takes `inputMode` and
  `maxLength`; `Stack` can be the page (`as="main"`, `inset="page"` with the safe-area bottom).
- **API client:** keeps `Retry-After` (lockout minutes) and fills `{path}` parameters, encoded.
- **Dates:** `lib/dates.formatDateTime` with `date-fns-tz` (`formatInTimeZone`, en-GB locale,
  24-hour), in the device timezone until the profile timezone (T09). `date-fns` and
  `date-fns-tz` are on the project's dependency list.
- **e2e stack:** `scripts/e2e_stack.sh` makes a fresh `lifeos_e2e` database on the local
  PostgreSQL and runs the API with `ENV=local` on port 8001; `vite preview` serves the built app
  on `http://localhost:4174` (a secure context for WebAuthn) and forwards `/api` (`LIFEOS_API`).
  Test-only helpers in `server/tests/e2e/` (`prepare`, `invite`, `expire_recent_auth`) refuse any
  database that is not local and named like `lifeos_e2e`, and `prepare` also requires its
  maintenance connection to be the same local server (`guard.py`, tested). Invites go through
  `AuthService`, as the admin console will (T44). `npm run test:e2e` builds Ladle and the app.
- **Clock set back:** any backward wall-clock step while away locks, including a small automatic
  correction; that costs at most an extra unlock and closes the "set the clock back" route.
- **One e2e database URL:** Playwright passes `tests/journeys/stack.ts`'s URL to the stack script
  as `E2E_DATABASE_URL` and to the helpers as `DATABASE_URL`, so the API and the helpers use the
  same database; the script's own default is only for running it by hand.
- **Journey notes:** recent authentication is ended with `expire_recent_auth` (as after 5
  minutes) so "Confirm it's you" is proven with the real authenticator; each new passkey on an
  existing account uses a fresh simulated authenticator (a new phone, J11), because an
  authenticator already holding her credential is excluded; the second-device step runs last,
  because the copied passkey's signature counter drifts from the phone's and the server rightly
  refuses a counter that goes back (12.3; real synced passkeys report 0).
