    `src/sw.ts`).
  - `src/lib/push/`: support and permission state, subscribe on tap, re-register on start.
  - `src/ui/NotificationPermissionCard/` (spec 5.5).
  - `src/features/onboarding/NotificationsScreen.tsx` (`/setup/notifications`).

  CR-027 makes a direct, pinned dependency.

## Decisions

- **Sender:** `notify/sender.py` wraps `pywebpush.webpush_async` (async, aiohttp) and turns the
  push service's answer into an outcome (delivered, gone, retry, rejected) for the dispatcher
  (T30). pywebpush and py-vapid use `cryptography` internally; our code imports it only in
  `platform/crypto.py` (VAPID key generation and the public key of a private key). mypy ignores
  pywebpush's missing type information (an override in `pyproject.toml`).
- **VAPID keys:** the 14.3 secrets as files (`vapid_public_key`, `vapid_private_key`,
  `vapid_subject`), the private key as the raw 32-byte scalar in base64url (what VAPID tools
  print). Start-up stops if the pair does not match or the subject is not `mailto:`. In
  `ENV=local` without them a pair is generated per process (browsers subscribed to an earlier one
  re-subscribe on their next start). Generating production keys is part of T15's secrets.
- **Endpoint allowlist (security):** the server POSTs to a subscription's endpoint, so only the
  browsers' push services are accepted — `fcm.googleapis.com`, `updates.push.services.mozilla.com`,
  `web.push.apple.com`, `*.push.apple.com`, `*.notify.windows.com` — over https on the default
  port; in `ENV=local` also `127.0.0.1`/`localhost` (the test and e2e fake push services).
- **Re-registering on start (10.5):** 9.2 has no "list my subscriptions" endpoint, so "compare
  with the server list and re-register if missing" is done by saving the current subscription
  again on every start (an idempotent upsert by endpoint that refreshes keys and session and
  turns it back on), subscribing anew if the browser dropped it. Never asks for permission.
- **An endpoint of another account** is refused (409) and left alone: RLS hides the row, so the
  upsert runs in a savepoint and reports the refusal.
- **Test push:** like every nudge it is a `reminders` row (spec 10 intro; 10.2 `test`: created by
  `/push/test`, fire time now). `POST /push/test` writes it (`sending`, attempt 1, `dedupe_key`
  `test:<id>`, payload `{title, body, url, actions}` encrypted with her DEK), sends the 10.7 `test`
  message with that `reminder_id` (discreet mode applies) to every active subscription, then marks
  it `sent` with `sent_at`, or `failed` when no device accepted it, and answers `{delivered: n}`;
  no subscription → 409. 404/410 turn a subscription off; other failures count (`failure_count`);
  retries are the dispatcher's (T30); the inbox (REM-5) lists it once T30 builds the inbox.
  `discreet_notifications` and her wrapped DEK are read directly, as the dispatcher will (10.3:
  `user_settings`, `users(id, timezone, dek_wrapped)`).
- **Endpoint check before every send:** the allowlist is checked when saving and again before
  each POST; a stored endpoint that no longer passes is turned off and never called. The check
  refuses anything URL parsers can read differently (user info, backslashes, whitespace, control
  characters, explicit ports), and host labels must be ASCII letters, digits and hyphens (no empty
  labels, percent encoding or other scripts), so it agrees with the HTTP client about the host.
- **One bad subscription never stops the rest:** any unexpected send error (keys that are not a
  key, an endpoint the HTTP client refuses) is `rejected` for that subscription; only the
  error's type is logged.
- **No redirects (CR-027 C1):** pushes go through an `aiohttp` session that does not follow
  redirects; a redirect is `rejected`. `aiohttp` (pywebpush's own transport) is pinned in
  `pyproject.toml`.
- **A session that ends turns off its device (CR-027 B1):** sign-out, revoking a session (AUTH-5)
  and the app lock's fifth wrong PIN (AUTH-6) disable that session's subscriptions in the same
  transaction (`notify.service.stop_session_notifications`, called by the auth service). Saving
  the subscription after the next sign-in (10.5) turns it back on. An admin recovery invite
  (AUTH-8, CR-018), which revokes all her sessions as `lifeos_admin`, leaves them on: its security
  notice must reach her devices, and that role has no rights on `push_subscriptions`.
  A subscription whose session ends some other way (that recovery, or idle/absolute expiry)
  stays on for now: CR-028 (approved 2026-10-09) has the T30 dispatcher send only to subscriptions
  with a live session, and after recovery send the account notice first, then turn them off.
- **"Another account" only for the RLS refusal:** the subscription upsert reports 409 only for
  SQLSTATE 42501 (the policy refused it); any other database error is raised.
- **Device label:** cleaned as every string (9.4: trimmed, control characters stripped, NFC);
  `clean_text` moved to `app/platform/text.py` so modules share it.
- **Service worker (10.5):** handlers are pure (`lib/sw/push.ts`). An unreadable push still shows
  a neutral notification ("Life OS" / "You have a reminder"); urls are app paths only, resolved
  the way the browser will before the check (tabs and newlines dropped, backslashes as slashes,
  dot segments removed), and a result that starts with `//` (from `/.//host`) is refused;
  the icon and badge are the 192 px app icon. "In 15 min" posts `{preset: "15m"}` to the snooze
  endpoint with an `Idempotency-Key` too: a fresh UUID (spec 9.1); "Taken" uses `reminder_id` as
  10.5 says. The dose and snooze endpoints come with T30 and the medication tasks.
- **VAPID key rotation:** on every start the app compares its subscription's
  `applicationServerKey` with the server's key and, if they differ, drops the subscription and
  subscribes anew (spec 15 "rotate VAPID keys (clients resubscribe on next open)"), so a new
  local key per process (or a rotated production key) is picked up.
- **A resubscribe keeps the device label:** the service worker's `pushsubscriptionchange` sends no
  label, so the upsert keeps the saved one.
- **Fail closed:** only a push service's 201/202 counts as delivered; any other return is
  `rejected`.
- **Opt-in journey:** the browser's prompt and `PushManager` are stubbed (spec 15 "push permission
  mocked"; headless Chromium has no push service); everything from the app's subscribe call to the
  fake push service is real.
- **Opt-in screen:** `/setup/notifications` (signed in) with the `NotificationPermissionCard`
  (spec 5.5): turn on (permission asked only in the tap), send a test, denied steps per platform,
  install first on an iPhone tab, unsupported. It is reached from the setup wizard (ONB-2, its
  task); Settings shows the state later (T32).
- **Browser tests:** headless Chromium has no push service and the default headless shell has no
  notifications, so the push journeys run in full Chromium ("new headless"); the test push goes
  to a fake push service run by the test; the service worker's push handler is driven with
  DevTools' `ServiceWorker.deliverPushMessage`. Headless Chromium has no notification centre and drops a
  shown notification within half a second (measured: listed at 0 s, gone at 0.5 s), so finding
  it with `getNotifications()` was a race that failed under load. The journey records what the
  real service worker passes to `showNotification` (the call 10.5 specifies) and still shows it;
  a renamed `push` listener fails it (checked).
- **API client:** a success with an empty body (the subscription's 201) returns nothing.
- **Denied steps:** per place (ONB-3; 10.6: Android pushes in a Chrome tab too): iPhone, Android
  app, Android Chrome tab (site settings), computer. The iPhone path (Settings → Notifications →
  Life OS) and the Android ones need a check on real devices (Ibrahim, with T15). Another iOS
  browser never reaches "denied" (it is "install first").
- **Card layout:** `NotificationPermissionCard` is built on `Card` (one card style); its action
  is full width like other card actions. The empty status line stays mounted (so it is announced)
  but takes no space; the denied badge keeps its shape with a `--danger` outline.
- **Offline:** a network failure says "We couldn't reach Life OS…" (`copy.common.networkError`),
  as other screens do, instead of blaming her phone.
- **Idempotency of the push endpoints:** the 9.1 idempotency store does not exist yet (no task
  has built it); saving and removing are idempotent by endpoint, and a replayed test push only
  sends twice. The task that builds the store covers these routes.
- **Done-when "test push received on Ibrahim's phone":** moved to T15 by CR-027 (A1); the closest
  check here is the full-Chromium journey through the real service worker and a real push to a
  fake push service.
