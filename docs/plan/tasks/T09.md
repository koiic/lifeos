## Decisions

- **Module:** `/me` lives in `core` (spec 6.2 names no owner for profile and settings; `core` is
  "the shared core that later life areas will reuse"). It reads and writes `users` and
  `user_settings` (RLS: her rows only). Health data comes through the `health` service
  (`health_mode`, `seed_symptoms`), never its repo.
- **Seeding (7.4):** in the registration transaction (passkey and password), so an account never
  exists without its symptoms; `system_key` in snake case, `sort_order` in 7.4's order, names
  ("Cramps", "Back pain", …) encrypted (`{v, name}`, AAD `symptoms:payload_enc:id:user_id`).
- **Health mode:** `standard` until a health profile exists (the setup wizard or Settings set it,
  ONB-2/SET-4); the profile's AAD uses her user id as the row id (its primary key).
- **Versions (CR-004):** `version` = `updated_at` (RFC 3339, microseconds), maintained by the
  0001 trigger (`clock_timestamp()`). `PATCH` needs `If-Match` (quotes optional): missing → 428;
  not current (or unreadable) → 409 problem+json with `current` and its `ETag`. `GET /me` carries
  both versions in the body (two resources, so no single `ETag`). An unchanged value is not
  written and keeps the version.
- **What she can change:** `PATCH /me`: `display_name` (9.4, 1–100), `timezone` (an IANA zone).
  `PATCH /me/settings`: `theme`, `week_start` (1 = Monday … 7 = Sunday, ISO), `temp_unit`
  (C/F), `checkin_time`, `quiet_start`, `quiet_end` (`HH:MM`, start ≠ end), `notif_prefs` and
  `optional_fields` (any subset, merged), `discreet_notifications`. Not here: the lock PIN and
  timeout (`/auth/app-lock`), `time_format` (24-hour only, no requirement asks for 12), consent
  (`/me/consent`), appointment reminder defaults (APT-2) and onboarding completion (ONB-2), which
  their tasks add.
- **Reminders (10.2):** a change to timezone, check-in time, quiet hours or notification types
  publishes `settings.changed` `{fields: [...]}` (names only, 7.2); T30 subscribes. Until then
  the relay keeps the events and warns about the unconsumed topic.
- **Consent (CR-030):** `POST /me/consent {version}`; the current version is `"1"`; stored once
  (consenting again returns the first record), audited as `user.health_consent` with her IP hash.
- **Timezone (CR-030):** `X-Timezone` is used only to compute `device_timezone` (an IANA zone or
  null) and `timezone_differs`; nothing is stored. T17 prompts and auto-sets.
- **Idempotency (9.1), temporary gap:** `Idempotency-Key` is accepted and ignored; no store
  exists yet. A replayed PATCH is refused by its version (409) and the offline queue would show
  "Couldn't sync" for a write that was applied; a replayed consent changes nothing. The store
  arrives with T18 (its done-when: "idempotent replay"), which must also cover `/me`,
  `/me/settings` and `/me/consent` — raised with Ibrahim, since T18's scope names daily logs.
- **9.4 strings:** every string field is cleaned before it is checked (`timezone`, the consent
  `version`, `display_name`); `week_start` is a strict integer (`"7"` and `true` refused), like
  the strict booleans.
- **409 contract:** typed per resource (`ProfileConflict.current: Profile`,
  `SettingsConflict.current: Settings`) in OpenAPI and `schema.d.ts`, so the client gets a typed
  `current`. The conflict error keeps her profile out of its `repr` (never logged).
  `platform/errors.py` documents a typed problem (a model holding every required `Problem`
  field and requiring it) as `application/problem+json` with its own schema; the contract test
  (`tests/platform/test_openapi_contract.py`) still requires problem+json and only problem+json
  for every error, and now accepts such a typed problem (seen failing first, with a new test
  that the two 409s carry `current`).
- **Column whitelist:** the repo builds `SET` lists only from `PROFILE_WRITABLE` /
  `SETTINGS_WRITABLE` and refuses any other name (Pydantic `extra="forbid"` already does).
- **Health profile AAD:** `health_profile:payload_enc:<user_id>:<user_id>`; the task that writes
  health profiles (SET-4, `/health/profile`) must use the same.
- **Seeding rollback:** seeding runs inside the registration transaction, so a registration that
  fails after it leaves no rows; not tested separately (no failure point after seeding can be
  forced without a fault-injection hook).
- **API contract:** `server/openapi.json` and `web/src/lib/api/schema.d.ts` regenerated for the
  four routes.
- **Design review:** not run: the only `web/` change is the regenerated API types
  (`schema.d.ts`); no UI.
