## Decisions

- **Wake-up "on NOTIFY":** a statement-level `AFTER INSERT` trigger on `outbox_events` queues
  `outbox.relay` in the same transaction as the event; Procrastinate's own NOTIFY then wakes the
  worker at once. The queueing lock `outbox.relay` collapses many inserts into one queued relay,
  and its unique violation is caught inside the trigger.
- **At-least-once relay:** the relay locks a batch (`FOR UPDATE SKIP LOCKED`, as `lifeos_jobs`),
  queues the jobs — committed on Procrastinate's own connection — and only then marks the events
  processed and commits. If queueing fails or the process dies, the batch stays unprocessed and is
  relayed again; jobs are idempotent by spec (rebuild "idempotent", horizon "idempotent via
  `dedupe_key`") and the per-user queueing lock drops duplicates still waiting. A backlog is drained
  batch after batch in one run.
- **Per-user serialisation:** queueing lock `<task>:<user_id>` (no duplicate waiting) plus
  Procrastinate `lock` `user:<user_id>` (two jobs for one user never run at the same time).
- **Unknown topics stay unprocessed** (warning with topic and count only): during a deploy an older
  worker must not consume events a newer API wrote (e.g. `settings.changed` regenerating reminders).
  Topics emitted before their consumer exists (e.g. T18 before T27) are relayed when it arrives.
- **Job arguments** are `user_id` only (outbox bodies hold ids only and are not forwarded yet).
- **Roles at connect:** engines and the Procrastinate pool set their role (`lifeos_app` or
  `lifeos_jobs`) at connect, so local and CI behave like production login roles (T03 security
  finding: development should run under RLS). Outside local the API checks at start-up that its
  login itself is `lifeos_app` (no SET ROLE over a stronger login that `SET ROLE NONE` could undo);
  the worker gets the same check with its container healthcheck (T15).
- **Queue privileges:** `lifeos_jobs` has full use of schema `jobs`; `lifeos_app` may only queue
  (EXECUTE on `procrastinate_defer_jobs_v1`, INSERT on job and event rows, SELECT of `id`);
  `lifeos_admin_ro` reads only the aggregate view `jobs.queue_stats`, never per-job rows (task names,
  locks and arguments would show when Zee logged). Recorded in the CR-003 addendum for the spec sync.
- **Job arguments are untrusted ids:** `defer_for_user` only ever passes `user_id`; every job loads
  its rows under RLS for that user and never uses `lifeos_jobs` or dispatcher privileges for work an
  argument drives. Procrastinate logs job calls in free text, so arguments must stay ids only.
- **Finished jobs are deleted after 7 days** (daily `jobs.prune_finished`, data minimisation 12.6).
- **Procrastinate's schema is vendored** (`migrations/procrastinate_3_10_0_schema.sql`) so migration
  0002 is deterministic; a guard test fails when the installed version differs. Upgrading means a new
  migration with Procrastinate's schema deltas and a new vendored file.
- **The trigger swallows only the relay's queueing-lock violation**
  (`procrastinate_jobs_queueing_lock_idx_v1`); anything else is raised. Search paths end with
  `pg_temp`.
