## Decisions

- **Registration state between options and verify:** `register/verify` receives `{token, name,
  email, credential}` again and re-validates the invite and fields; the new user's id is the
  registration challenge's id (`auth_challenges.user_id` cannot reference a user who does not exist
  yet), so the WebAuthn user handle and the account id are the same UUID v7.
- **Challenges** are looked up by the challenge in the client data, used once, valid 5 minutes.
- **Invite email:** when an invite carries an email, the registration email must match it
  (case-insensitive); otherwise 403. A registration email already in use → 409.
- **Recovery codes:** 10 codes of 12 base32 characters (60 bits) shown once, stored argon2id
  (m = 19 MiB, t = 2, p = 1: the codes are high-entropy, unlike passwords). Recovery follows
  CR-013: `{"next": "add_passkey", "options": …}`, no session until the new passkey is verified;
  if that step fails the code is spent (she has ten). Every attempt runs exactly 10 hash checks and
  the same queries (an unknown email uses a random id that RLS matches to nothing), so responses
  and timing do not reveal accounts or how many codes are left. The hashing runs with no
  database connection held (read codes, hash, then spend with a conditional update and insert the
  challenge), so slow unauthenticated attempts cannot exhaust the connection pool.
- **Sessions:** cookie `lo_session` = base64url of 32 random bytes; `expires_at` slides to
  now + 30 days (never past created + 180 days) at most once an hour of use; any expired, revoked or
  unknown session → 401 problem+json.
- **Keyring (CR-011):** `lifeos_kek` lines `<version> <base64>`; in `ENV=local` only, without the
  file, a fixed all-zero development key (version 1) is used so local data survives restarts. It is
  never accepted outside local.
- **Algorithms:** ES256 and RS256 only (the library also defaults to EdDSA).
- **Time:** services take `now`; the API uses a `clock` dependency that tests replace.
- **RP ID:** `WEBAUTHN_RP_ID` defaults to the `APP_ORIGIN` host and must be that host or a parent
  domain of it (WebAuthn rule), checked at start-up.
- **Sign-out** always answers 204 and clears the cookie, revoking the session when the cookie names
  one (an expired cookie must still be clearable).
- **Errors:** invalid invite 403, email taken 409, registration verification failure 400, any
  sign-in or recovery failure 401 with one fixed body; malformed credential JSON is a 401/400, not a
  500.
- **Input limits** (spec leaves them open): name 1–100 characters after cleaning; email ≤ 254
  characters (RFC 5321), shape `local@domain.tld`; invite token ≤ 200 characters; recovery code
  input ≤ 64 characters. Names and emails get the 9.4 string rules (NFC, control characters
  stripped, trimmed).
- **Invite status** leaves out `email` when the invite has none (9.2 `{valid, email?}`); an
  invalid token answers `{"valid": false}`.
- **Credential bodies** stay `dict[str, Any]`: the WebAuthn JSON is parsed and verified by
  py_webauthn, so a second Pydantic model of it would duplicate the parser. Options responses are
  the `WebAuthnOptions` model (open schema).
- **Challenge table growth:** each new challenge deletes challenges expired over a day ago, so the
  unauthenticated options endpoints cannot grow the table without bound; T07 must also rate-limit
  `/auth/signin/options`, `/auth/register/options`, `/auth/signin/recovery` and
  `/auth/passkeys/verify` per IP hash, separately from failed sign-in counting. No index on
  `auth_challenges.challenge` (the table stays small; a schema change would need a CR).
- **Registration fields vs challenge:** the challenge is bound to its invite, not to the email and
  name; an invite without an email lets its holder change them between options and verify. Accepted:
  only the invite holder can, and the stored account is what verify received.
- **Sign count** is stored only if higher than the stored one (or both zero), so concurrent
  sign-ins cannot move it backwards; such a race fails the later sign-in.
- **A new sign-in** (register, passkey, recovery passkey) ends the session the browser's cookie
  still named.
- **`Cache-Control: no-store`** on every successful `/api/v1/auth/*` response (recovery codes,
  cookies). Error responses carry no secrets and are left as the platform sends them.
- **For T08:** `/auth/passkeys/verify` without a session accepts only an unused `add_passkey`
  challenge, which today only recovery creates. When T08 adds the signed-in path, its challenges
  must be told apart (require the session and check the challenge's `user_id` equals the
  session's), so the session-less path cannot complete them.
- **Transactions:** services use `app.platform.db.user_transaction` / `system_transaction` and the
  `Database`/`Transaction` names, so only `repo.py` imports SQLAlchemy (`user_transaction` moved
  from `platform/jobs.py`).
