## Decisions

- **Recent auth (CR-017, Ibrahim):** `sessions.reauth_at`, set at sign-in (a new session is a
  fresh verification) and by `/auth/reauth/verify`; recent = less than 5 minutes ago, for this
  session only. Refusal: 403 problem+json "Confirm it's you to continue.". Needed here (12.3 and
  CR-020) by recovery-code regeneration, removing a passkey, adding a passkey (options and
  verify), changing or clearing the PIN, and issuing a recovery invite (the admin's session);
  export download and deletion use `AccountService.require_recent_auth` in their tasks.
- **Re-auth:** `/auth/reauth/options {purpose: reauth|unlock}` lists her own passkeys
  (`allowCredentials`), UV required, challenge bound to her account; `/auth/reauth/verify` takes
  `{credential}` or `{password, totp}`. Both are attempts like sign-ins (AUTH-7 events
  `signin_passkey` / `signin_password`, IP lockout; the password path also the account lockout).
  An `unlock` re-auth also counts as recent auth (it is a passkey verification).
- **Sessions list:** her live sessions (not revoked, not expired), oldest first, with device
  label, created/last-seen and the current flag; `{items, next_cursor: null}` (9.1 shape; her
  sessions always fit one page). Revoking: her own only (404 otherwise), logged as `revoke`;
  revoking the current one also clears the cookie.
- **Device labels:** "<device> <browser>" from fixed lists (iPhone, iPad, Android, Chromebook,
  Mac, Windows, Linux × Edge, Firefox, Chrome, Safari), else "Unknown device"; nothing from the
  header itself is stored.
- **Passkeys (CR-019):** `GET /auth/passkeys` lists id, nickname, created/last used, backed up (no
  key material). Adding while signed in: options exclude her existing passkeys; verify needs her
  own `add_passkey` challenge and creates no new session (it is counted against the 9.1 limit and
  slides the session like any signed-in request). Without a session, `/auth/passkeys/verify` is
  the recovery-code path (CR-013); it cannot tell a signed-in challenge from a recovery-code one
  (no column), so every revocation (sign-out, revoking a session, the PIN lockout, a recovery
  invite) spends the account's pending passkey-add, re-auth and unlock challenges: a revoked
  session's challenge can never mint a new session. Issuing a passkey-add challenge share-locks the
  session row in the same transaction, so a revocation cannot slip in between the check and the
  insert. A session that is over the 9.1 limit or not activated is refused at
  `/auth/passkeys/verify` (429/403), never treated as cookie-less. Residual: a live, recently
  authenticated session can finish its own challenge without the cookie and get a second session
  (it already has one).
- **Last sign-in method:** passkeys plus a password with confirmed TOTP; recovery codes are not a
  sign-in method. Removing the last one → 409 "This is your last way to sign in." Her passkey rows
  are locked (`FOR UPDATE`) before counting, so two removals at once cannot both pass. Ownership
  is checked first, so another user's id is 404 whether or not this session is recent.
- **Recovery codes:** regeneration deletes all old codes and returns 10 new ones once (200,
  `no-store`).
- **App lock:** `PUT /auth/app-lock {pin?, timeout_s?}` — `pin` six digits to set, `null` to clear,
  absent to keep (changing or clearing it needs recent auth, CR-020; the timeout alone does not);
  `timeout_s` 60–3600 seconds (spec default 300). The PIN is stored Argon2id (password
  parameters). Unlock (CR-021, Ibrahim): each try is counted on this session's
  `pin_failures` *before* the PIN is checked (an atomic row update, so concurrent tries get
  distinct numbers and at most five are checked); a good PIN or any passkey verification on this
  session resets it; the fifth wrong try (or any try past it) revokes the session, spends its
  pending challenges and clears the cookie ("5 tries then full sign-in required"); no PIN → 409.
  Every try is also logged (`pin_unlock`). The PIN unlock is not "recent auth" (12.3 names
  passkey or password).
- **Recovery invites (AUTH-8, CR-018):** `POST /admin/users/{id}/recovery-invite` (admin role,
  else 403; the admin's recent auth, CR-020; unknown account 404) creates an invite with
  `recover_user_id`, her email, 24 hours, and in the same transaction revokes her earlier unused
  recovery invites (only the newest link works), revokes all her sessions and spends their
  pending challenges, writes `audit_log`
  (`admin.recovery_invite`, actor, target, IP hash) and an outbox event `auth.security_notice`
  `{"event": "recovery_invite"}` for the notify module to send the 10.7 "Account notice". Returns
  `{token, link: "/recover?token=…", expires_at}` once. `/auth/recover/options {token}` and
  `/verify {token, credential}`: only recovery invites (registration and invite-check refuse them,
  and `/recover` refuses registration invites); the challenge is bound to the invite and account;
  the new passkey is stored, all old recovery codes are deleted, 10 new ones are returned once, the
  invite is spent (any other unused recovery invite of hers is revoked) and she is signed in.
  Logged as `recovery`.
- **Admin endpoints** need a signed-in admin session (`require_admin` on `users.role`). Writes run
  as `lifeos_admin` (CR-022, Ibrahim): its own connection (`database_admin_write_url`; locally the
  default URL with that role), verified at start-up outside local; grants allow only invites,
  session revocation, spending challenges, the audit log and the `auth.security_notice` outbox
  topic (a policy), plus queue-only rights so the outbox wake-up trigger can queue the relay. No
  health table, credential or key. Revoke only: a policy stops it un-revoking sessions, and a
  trigger (`admin_cannot_undo`) stops it clearing `invites.revoked_at` or `auth_challenges.used_at`.
  Follow-up (security review, optional): making the outbox wake-up trigger SECURITY DEFINER would
  let both `lifeos_app` and `lifeos_admin` drop their direct `jobs` INSERT rights — a CR for later.
  **For T44:** `POST /admin/users/{id}/revoke-sessions` (and account deletion) must also call
  `repo.spend_pending_challenges` in the same transaction. Without the connection admin writes answer 503. The admin API
  module uses the auth module's HTTP dependencies (`require_session`, `Client`, `Now`) — the auth
  module's public HTTP interface — and the service returns the invite's expiry.
- **Outbox:** `app.platform.outbox.publish` writes an event in the caller's transaction (first
  writer of events; ids and kinds only).
