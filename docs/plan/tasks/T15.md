## Plan

- `web/functions/api/[[path]].ts`: Cloudflare Pages Function proxy forwarding `/api/*` to `ORIGIN_URL` with Access service-token headers (`CF-Access-Client-Id`, `CF-Access-Client-Secret`), preserving method, query, headers, cookies, and body without logic (ADR-0001, spec 14.1).
- `web/public/_headers`: Cloudflare Pages static security headers matching spec 12.4 (strict CSP, HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, COOP).
- `server/Dockerfile`: Multi-stage production container for API, worker, and migrations. Non-root user (`appuser`), read-only root FS, `/api/v1/readyz` healthcheck, `uv`-based installation.
- `infra/docker-compose.yml`: Production Docker Compose definition with `cloudflared`, `api`, `worker`, `migrate`, `postgres`, `backup`. Per CR-015, `api` and `postgres` publish no host ports; all traffic enters via `cloudflared`. Secrets mounted from `/run/secrets/`.
- `infra/runbooks/`: Operational runbooks for VPS setup, Cloudflare Pages Function & Tunnel setup, secret provisioning (`lifeos_kek`, VAPID, database credentials), and deployment.
- Tests: unit tests for Pages Function proxy, security headers validation, and Docker Compose structure / security checks.

## Decisions

- **Pages Function proxy:** Implemented in `web/functions/api/[[path]].ts` as pure TypeScript using standard Fetch `Request` / `Response`. Re-exported proxy function is tested in Vitest.
- **Network trust over token trust (CR-015):** The API is reachable only through `cloudflared` on the Docker bridge network; no host ports are published for `api` or `postgres`.
- **Static security headers (spec 12.4):** Placed in `web/public/_headers` so Vite copies it directly to `dist/_headers` on build.
- **Container security (spec 14.2):** `api` and `worker` run as non-root user `appuser` (UID 10001) with read-only root filesystems and temporary storage in `tmpfs: /tmp`.
